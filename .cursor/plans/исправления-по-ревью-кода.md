# Исправления по ревью кода «Вышибалы»

Ревью охватывает собственный код подсистемы `УправлениеСеансами`: общие модули `НастройкиАдминистрированияКластеров`, `СеансыИнформационныхБаз`, `ПраваУправленияСеансами`, `ПротоколУправленияСеансами`, форму обработки `УправлениеСеансами`, модули трех справочников, регистров `РазрешенныеИнформационныеБазы` и `ПротоколОперацийУправленияСеансами`, правки в `УправлениеДоступомПереопределяемый` и `ОбновлениеИнформационнойБазыВШБ`.

План уже учитывает встречную оценку [оценка-ревью-кода.md](оценка-ревью-кода.md). По ней:

- снят ошибочный сценарий повышения прав, пункт 1 понижен до защитного;
- для пакетного завершения выбран вариант А (KISS);
- пункт о лишних обращениях к RAS сужен до формы;
- уточнены пункты 7, 8 и 9.

На момент ревью EDT не показывает ошибок, только 19 замечаний уровня MINOR. Проблемы ниже касаются логики работы, статический анализ их не видит.

Порядок работ: 2, 3, 4, затем 1 и остальные.

## 1. Проверки прав без учета привилегированного режима (защитный контракт)

**Что в коде.** Функции `ПраваУправленияСеансами` проверяют права через `Пользователи.ЭтоПолноправныйПользователь()` и `Пользователи.РолиДоступны(...)` с параметрами по умолчанию. При `УчитыватьПривилегированныйРежим = Истина` (значение по умолчанию) обе функции возвращают Истина, если установлен привилегированный режим.

**Действующей уязвимости нет.** Платформа сама выключает привилегированный режим при выходе из метода, в котором его включили. На это опираются сама БСП (`Пользователи.РолиДоступны` включает режим и возвращает результат без сброса) и стандарт #std485 (пример `ТекущийПользователь()`). Когда исключение из `НастройкиАдминистрированияКластеров.ДанныеУчетнойЗаписи` доходит до перехвата в `ЗавершитьСеансы`, `ДобавитьСостояниеКластера` или `ДобавитьСостояниеБазы`, кадр уже снят и режим выключен. Сценарий «режим залип после исключения, ограниченный оператор завершил веб-клиент» не срабатывает.

**Зачем все равно менять.** Проверка прав должна отвечать на вопрос «какие роли у пользователя», а не «включен ли сейчас привилегированный режим». Иначе любой будущий вызов проверки из привилегированного блока, например из фонового задания или из кода внутри `УстановитьПривилегированныйРежим(Истина)`, молча снимет ограничения оператора.

**Исправление.**

- Роли операторов проверять через `Пользователи.РолиДоступны(ИменаРолей, , Ложь)`. Эта функция сама учитывает полноправного пользователя, поэтому связку `ЭтоПолноправныйПользователь() Или РолиДоступны(...)` в `МожноЗавершатьСеансы` и `ИнформационныеБазыДоступныБезОграничения` можно заменить одним вызовом.
- В `МожноУправлятьБлокировкой` и `МожноЗавершатьСеансыПакетно` ролей операторов нет, там достаточно `Пользователи.ЭтоПолноправныйПользователь(, , Ложь)`.
- Вызовы собрать в две служебные функции модуля, чтобы параметр `Ложь` не потерялся ни в одном месте.
- Обертывать чтение пароля в `ДанныеУчетнойЗаписи` в `Попытка` не обязательно, только для единообразия с `РазрешенныеИнформационныеБазы`: в самом методе исключение никто не перехватывает.

## 2. Завершение сеанса только по номеру (высокий приоритет)

**Проблема.** `ЗавершитьСеансИнформационнойБазы` и `ЗавершитьСеансыИнформационнойБазы` строят фильтр БСП только по полю `Номер`. Платформа использует номера сеансов повторно. Между обновлением списка в форме и нажатием «Завершить» под тем же номером может оказаться сеанс другого пользователя, и он будет завершен.

Для ограниченного оператора проверка типа клиента тоже идет по сеансу, который сейчас носит этот номер. Имя пользователя для протокола приходит с клиента (`ОписаниеСеанса.Пользователь`) и с данными RAS не сверяется, поэтому протокол может записать не того пользователя.

**Исправление по одному сеансу (основной путь интерфейса).**

- В описание завершаемого сеанса (форма, `ПомеченныеСеансы`) добавить `НачалоСеанса`. Колонка `Сеансы.НачалоСеанса` в форме имеет тип «Дата и время», точность совпадает с `МоментСозданияСеанса` из RAS.
- Фильтр строить тремя условиями `Равно` по полям описания сеанса БСП: `Номер`, `ИмяПользователя`, `МоментСозданияСеанса`. Так завершается ровно тот сеанс, который пользователь видел в списке.
- Собирать фильтр одной служебной функцией.
- Для ограниченного оператора в `ОписаниеОшибкиЗавершенияПоТипуКлиента` сверять имя пользователя и время начала со строкой из свежего списка RAS. Если они не совпадают, считать сеанс отсутствующим.
- Текст протокола об успешном завершении поменять на «завершен или уже отсутствовал». Если сеанса с такой тройкой нет, БСП считает операцию успешной (пустой список после фильтра), и без отдельного запроса к RAS эти случаи не различить.

**Пакетное завершение: вариант А (KISS).**

- `ЗавершитьСеансыПакетом` остается одним вызовом `УдалитьСеансыИнформационнойБазы` с фильтром `ВСписке` по каждому из трех полей.
- Это не точная идентификация тройки. `ПроверитьУсловияФильтра` соединяет условия по И, поэтому независимые списки дают декартово произведение. Сеанс с номером из списка, именем из списка и временем создания из списка пройдет фильтр, даже если эти значения взяты из разных строк.
- Риск принят сознательно. Номер освобождается только после построения списка в форме, поэтому сеанс, который занял номер повторно, создан позже любого показанного сеанса. Ложное совпадение возможно, только если новый сеанс создан в ту же секунду, что и один из перечисленных. Пакетный режим доступен только полноправному пользователю, а форма уже предупреждает, что результат по каждому сеансу недоступен.
- Ограничение записать в комментарий к `ЗавершитьСеансыПакетом`.
- Вариант Б отклонен: один обход RAS с отбором точных троек в памяти. Он требует либо закрытой функции БСП `АдминистрированиеКластераRAS.СписокСеансов` (правка модуля БСП), либо собственного кода поверх `АдминистрированиеСервера` с повтором логики БСП (повторные попытки, сообщение пользователям). Оба пути противоречат правилу AGENTS.md: зависеть от моста и публичного API БСП, а не от его внутренностей.

**Обращений к RAS не прибавится.** `АдминистрированиеКластераRAS.УдалитьСеансыИнформационнойБазы` получает от RAS полный список сеансов базы, а фильтр проверяет на сервере 1С через `АдминистрированиеКластера.ПроверитьУсловияФильтра`. Дополнительные условия меняют только локальную проверку.

**Ловушка БСП.** `АдминистрированиеКластера.ДобавитьУсловиеФильтра` неверно добавляет второе условие, если фильтр был создан первым вызовом с `ВидСравнения.Равно`. В этом случае фильтр становится структурой `Поле = Значение`, при втором вызове копируется как есть, и `ПроверитьУсловияФильтра` падает на `Условие.Свойство`. Фильтр нужно создавать как `Новый Массив` и только потом добавлять условия. Одно условие `Равно`, как в текущем коде, работает.

## 3. Теряются причины, когда ни один сеанс не завершен (средний приоритет)

**Проблема.** Если ни один сеанс не завершен, `СеансыИнформационныхБаз.ЗавершитьСеансы` вызывает исключение «Не удалось завершить ни одного сеанса». Форма показывает только этот текст. Результаты по каждому сеансу с описанием ошибки уже собраны, но до пользователя не доходят. Оператор не видит, что случилось: нет прав на тип клиента, сеанс не найден или RAS недоступен.

**Исправление.** Возвращать массив результатов без исключения. Форма уже выводит неуспешные результаты через `ПоказатьРезультатыЗавершения`. При частичном успехе массив возвращается и сейчас. Протокол по каждому сеансу пишется в цикле до исключения, тут ничего не меняется.

## 4. Регламентное задание очистки протокола не работает (средний приоритет)

**Проблема.**

- У `ОчисткаПротоколаОперацийУправленияСеансами` в метаданных не задано «Использование» и нет расписания. Код задание нигде не упоминает: поиск по имени дает 0 совпадений. Задание никогда не запускается, и регистр `ПротоколОперацийУправленияСеансами` растет без ограничений, хотя константа `СрокХраненияПротоколаОперацийДней` обещает очистку.
- В `ПротоколУправленияСеансами.ОчиститьУстаревшиеЗаписи` нет вызова `ОбщегоНазначения.ПриНачалеВыполненияРегламентногоЗадания(Метаданные.РегламентныеЗадания.ОчисткаПротоколаОперацийУправленияСеансами)`. БСП требует его от обработчиков регламентных заданий: он проверяет, можно ли сейчас выполнять задание (блокировка, обновление ИБ, функциональные опции).

**Исправление.** В метаданных задания включить «Использование» и задать ночное расписание. В начало обработчика добавить вызов `ПриНачалеВыполненияРегламентногоЗадания`. Отдельная настройка задания в интерфейсе БСП не нужна: срок хранения задает константа.

Построчное `Удалить()` менеджерами записи в `ОчиститьУстаревшиеЗаписи` медленное на больших объемах. Это отдельная слабость, в эту правку ее не включать.

## 5. Обращения к RAS из формы (средний приоритет)

**Проблема.** Каждая операция БСП с RAS открывает новое подключение.

- **Открытие формы.** `СостоянияИнформационныхБаз` в `ПриСозданииНаСервере` синхронно запрашивает у RAS состояние блокировки каждой базы. При десятке баз и более форма открывается заметно долго, а одна недоступная RAS задерживает открытие на время таймаута.
- **Перемещение по дереву.** `ДеревоБазПриАктивизацииСтроки` сразу вызывает сервер и RAS. Перемещение стрелками по дереву дает по запросу к кластеру на каждую строку.

**Исправление.**

- При открытии формы строить дерево только из справочников, без опроса RAS. Колонки блокировки заполнять по команде «Обновить состояние» (там опрос всех баз остается явным действием пользователя). Для полноправного пользователя блокировка выбранной базы и так читается вместе с ее сеансами. Операторы читать настройки блокировки не могут (`ПроверитьПравоУправленияБлокировкой`), поэтому у них колонки заполнятся только по команде. `ДлительныеОперации` не нужны.
- Активизацию строки обрабатывать через `ПодключитьОбработчикОжидания` с задержкой около 0,2 с.

**Что не входит.** Завершение по одному сеансу так и остается одним вызовом `УдалитьСеансыИнформационнойБазы` на сеанс, со всеми его запросами к RAS и до 4 повторными попытками. Если собирать `ПараметрыАдминистрирования` один раз на операцию, уйдет только повторное чтение реквизитов и паролей, а число обходов RAS не изменится. Сократить их можно было бы вариантом Б из пункта 2, но он отклонен. Кэш параметров делать по желанию, как мелкую оптимизацию.

## 6. Повторный вызов исключения (низкий приоритет)

**Проблема.** В `НастройкиБлокировки`, `УстановитьНастройкиБлокировки` и `СеансыИнформационнойБазы` блок `Исключение` сначала вызывает `ПротоколУправленияСеансами.ЗаписатьОшибку(..., ИнформацияОбОшибке())`, а затем `ВызватьИсключение ОбработкаОшибок.КраткоеПредставлениеОшибки(ИнформацияОбОшибке())`. Новое исключение со строкой теряет категорию и стек исходной ошибки.

**Исправление.** Сохранять `ИнформацияОбОшибке()` в переменную в начале блока `Исключение` и пробрасывать ошибку через `ВызватьИсключение;`, как в `НастройкиАдминистрированияКластеров.ПроверитьПодключение`. Формы и так показывают `КраткоеПредставлениеОшибки`.

## 7. Перехват исключения внутри транзакции (низкий приоритет)

**Проблема.** `ПротоколУправленияСеансами.ЗаписатьВРегистр` перехватывает ошибку записи регистра и пишет ее в журнал. Его вызывают `ПриЗаписи` кластера, информационной базы, учетной записи и набора записей `РазрешенныеИнформационныеБазы`, то есть изнутри транзакции записи объекта. После ошибки СУБД транзакцию нельзя зафиксировать, и запись объекта все равно упадет, только с менее понятным сообщением «В данной транзакции уже происходили ошибки». Стандарт запрещает перехватывать исключения внутри транзакции без ее отмены.

**Исправление.**

- Если `ТранзакцияАктивна()`, исключение не перехватывать: изменение настроек и строка протокола фиксируются или откатываются вместе.
- Вне транзакции (завершение сеанса, блокировка) перехват оставить: сбой записи протокола не должен скрывать уже выполненную операцию с RAS.

## 8. Повторы кода (низкий приоритет)

- `СеансыИнформационныхБаз.ЗаполнитьСостоянияИнформационныхБаз` содержит два текста запроса, которые отличаются только отбором по `&РазрешенныеБазы`. Достаточно одного запроса с условием `(НЕ &ОграничитьСписокБаз ИЛИ ... В (&РазрешенныеБазы))`. Параметр `РазрешенныеБазы` передавать всегда: язык запросов не обрывает вычисление `ИЛИ`, и незаданный параметр даст ошибку.
- Порты по умолчанию 1545 и 1541 задаются и в `КластерыСерверов.ОбработкаЗаполнения`, и в `ПриСозданииНаСервере` формы кластера. Платформа вызывает `ОбработкаЗаполнения` при интерактивном создании, так что код формы лишний.
- UUID поставляемых профилей операторов (`e31e0989-...`, `d6043cd2-...`) записаны строками в `УправлениеДоступомПереопределяемый.ПриЗаполненииПоставляемыхПрофилейГруппДоступа` и в `ОбновлениеИнформационнойБазыВШБ.СоздатьГруппыДоступаОператоровТехподдержки`. Если изменить идентификатор в одном месте, обработчик обновления перестанет находить профиль. Вынести их в одну функцию. Идентификаторы групп доступа записаны только в обработчике обновления, их не трогать.

## 9. Операторы видят логины администраторов кластеров (низкий приоритет)

**Проблема.** Роли `ОператорТехподдержки` и `ОграниченныйОператорТехподдержки` имеют право чтения справочника `УчетныеЗаписиАдминистрирования` (`setForAttributesByDefault = true`). Нужно оно только потому, что `ДанныеУчетнойЗаписи` читает `ИмяПользователя` до привилегированного блока. Пароля в реквизитах нет, но операторы видят логины администраторов всех кластеров и баз.

Операторы также читают справочники кластеров и баз и видят подсистему. Поля `АдминистраторКластера` и `АдминистраторИнформационнойБазы` выведены на четырех формах, которые оператор может открыть:

- `КластерыСерверов.ФормаЭлемента`;
- `КластерыСерверов.ФормаСписка`;
- `ИнформационныеБазыКластера.ФормаЭлемента`;
- `ИнформационныеБазыКластера.ФормаСписка`.

**Исправление.** В таком порядке:

1. Скрыть поля учетных записей на этих четырех формах для пользователей без права на справочник учетных записей.
2. Читать `ИмяПользователя` в том же привилегированном блоке, что и пароль.
3. Снять с ролей операторов право чтения `УчетныеЗаписиАдминистрирования`.

Обработка `УправлениеСеансами` учетные записи не показывает.
